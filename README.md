# Core V3.0 — Корпоративный аудит

Desktop-приложение для автоматизации аудита розничной сети. Обрабатывает выгрузки из 1С, АСУС и Тандер Склад: анализ квантов, инвентаризационные описи, свод ОС/МБП, проверка Брак/Утиль, управление принтерами, работа с сетевыми папками, встроенный браузер, дашборд по письмам инвентаризации, табель ревизора и разметка Shadow Engine.

## О проекте

**Core V3.0** — внутренний инструмент аудитора розничной сети. Заменяет ручную обработку Excel-выгрузок из 1С, АСУС и Тандер Склад на автоматизированные сценарии с валидацией, подсветкой расхождений и формированием готовых отчётов. Дополнительно собирает и анализирует письма инвентаризации из Outlook, строит дашборд, ведёт архив, табель ревизора и размечает решения Shadow Engine.

**Область применения:**

- аудит потерь (анализ квантов);
- инвентаризация основных средств и МБП;
- сверка актов списания (Брак/Утиль);
- сборка паллет;
- ведение чек-листов инвентаризации;
- табель рабочего времени ревизора;
- подготовка стандартных комментариев для отчётов;
- аналитика по письмам инвентаризации (дашборд);
- архив завершённых инвентаризаций;
- разметка объяснений Shadow Engine (вкладка AI).

**Принципы разработки:**

| Принцип | Реализация |
|---------|-----------|
| Логика важнее формы | Работающий код не переписывается ради метрик |
| Данные отделены от кода | Правила хранятся в `JSON`, а не в `Python` |
| Тесты — на логику | Покрытие бизнес-правил, не UI |
| Единый стиль | Только SVG-иконки (Lucide), без эмодзи |
| Тёмная тема | Красный акцент `#D42626`, зелёный — только для успеха |

## Возможности

### Кванты — автоматический анализ потерь

- Загрузка `РТП.xlsx` (реестр товарных позиций) и `Кванты.xlsx` (отчёт потерь).
- Фильтрация позиций с потерями ≥ 1000 руб.
- **Три жёстких правила** (применяются первыми, не перезаписываются):
  - **Фрукты/овощи** — типовая причина «Пересорт на кассе», без номера БФ.
  - **Сырьё** (по ГР 20 или по наименованию ТП) — «Потери ТО (сырьё)», без номера БФ.
  - **Местный поставщик** (операции `Приход•Местный` и `Приход•Недовоз от поставщика`):
    - Излишек → «Ошибки в работе (Местный поставщик)» + «Нет номера БФ».
    - Недостача → «Потери ТО (Местный поставщик)» + «Нет номера БФ».
- **Мягкие правила** — коробочный недовоз/излишек, зеркальные отклонения, хищения.
- Распределение позиций между двумя ревизорами (по сумме потерь по убыванию, чётность).
- Правила вынесены в `data/kv_rules.json` — изменение без правки кода.
- Строгая маска причин в `data/kv_reason_schema.json` — валидация после анализа (причина, знак, документ).
- Экспорт файла `Позиции для РТП.txt` с кодами для выгрузки из Тандер Склад.

### ОС и МБП — свод инвентаризационных описей

- Парсер формы ИНВ-1 (инвентаризационная опись).
- Автоматический поиск строки-шапки по маркеру «количество, шт.».
- Выбор столбца с количеством из двух кандидатов («Фактическое наличие» и «По данным бухгалтерского учёта») — используется тот, где сумма значений больше нуля.
- Фильтрация служебных строк: шапка, нумерация, итоги.
- Автоподбор ширины колонок в результирующем файле.
- Опция «Убрать лишнее» — фильтр спецодежды, СИЗ и вспомогательных позиций. Список в `data/unwanted.json`.

### Брак / Утиль — сверка актов списания

- Сверка двух файлов по номеру документа:
  - «Выборочная проверка актов списания утиля»;
  - «Операции списания».
- Допуск по сумме настраивается (`BRAK_UTIL_TOLERANCE` в `config.json`).
- Подсветка расхождений красным в результирующем Excel.
- Автоподбор ширины колонок.
- Архивирование результата в `.zip`.

### Паллеты — сборка свода

- Обработка папки с файлами `XXXXXX.xls` / `XXXXXX.xlsx` (6 цифр — номер паллеты).
- № паллета берётся из имени файла.
- Сборка единого свода: `Отклонение` (Кол-во до − Кол-во после), `Сумма` (всегда 0).
- Все ячейки с границами, столбцы по ширине содержимого.
- Дополнительно создаётся `Файл инвентаризации.txt` — сводная по `Код товара` (сумма отклонений), формат строки `Код<TAB>Отклонение`, без шапки.

### Инвентаризация — чек-листы по дням

- Старт новой инвентаризации: ГМ, вариант (А–Ж), дата начала.
- Автокомплит ГМ через `QCompleter` (по коду и названию).
- Календарь в стиле приложения — выпадающий, тёмный, с подсветкой текущей даты.
- Автоматический расчёт даты окончания по выбранному варианту.
- Чек-лист по дням и сменам с общим прогрессом.
- Debounce-сохранение (300 мс) — снижает частоту записи на диск.
- Автосохранение чек-листа при переключении вкладки и при закрытии приложения (хуки `on_hide()` / `on_close()` в `BaseFrame`).
- Смена ГМ и завершение с архивацией.
- При завершении создаётся структура папок в `Готовые/Инвентаризации/{gm_code}_{start_date}/`: `1 сутки`, `2 сутки`, `3 сутки`, `4 сутки`, `5 суток`, `Итоговые`.
- Архив инвентаризаций — отдельная вкладка (см. ниже).

### Табель — рабочее время ревизора

- Свой календарь на месяц (воскресенье подсвечено красным).
- Три поля на день: **К** (командировка), **Д** (дорога), **Н** (ночь).
- Поля пустые по умолчанию, только целые числа.
- Автосохранение при вводе в `timesheet.json`.
- Строка для АСУЗ снизу + кнопка «Копировать».
- Сводка по 4 неделям месяца (только К).
- Итого по К + отдельно «Дорога (Д)» и «Ночные (Н)».

### Архив инвентаризаций

- Список завершённых инвентаризаций из `data/inventory_archive.json`.
- Карточка записи: ГМ, название, вариант, даты, итоговая сумма.
- **Клик по карточке** → открывается **встроенный дашборд** по этому ГМ.
- Кнопка «← Назад в архив» — возврат к списку.
- Записи **не удаляются**.
- Данные подгружаются мгновенно из кэша `DataManager`, затем асинхронно проверяется, не изменился ли файл.

### Дашборд — аналитика по письмам инвентаризации

Дашборд собирает данные **не из Excel**, а из **писем Outlook** (см. «Интеграция с Outlook»). Для выбранного ГМ показывает:

- **СВОДКА** — итоговая сумма по последнему письму (финальное, если есть).
- **ДИНАМИКА** — линейный график по **всем** письмам ГМ: точка за каждый день, подписи «N сутки» и даты, сумма над точкой, заливка под линией. Итоговая строка «За период: дата → дата» с дельтой (↑ / ↓ / =).
- **ТОП-3 ЗОНЫ** — три аналитические зоны с максимальным отклонением по модулю. Горизонтальные бары, процент от общей суммы.
- **АНАЛИТИЧЕСКИЕ ЗОНЫ** — круговая диаграмма + легенда со суммами и процентами. Зоны берутся из канонического списка: Алкоголь, Алкоголь НД, Косметика и Бытовая химия, Весовые конфеты, Заморозка, Непрофиль, Охлажденка, Продукты, Сигареты, Фреш.
- **ПРОЧИЕ МЕРОПРИЯТИЯ** — все события, не относящиеся к зонам: инвентаризация МХ, перепроверки, контроль и т.д.
- **ЧАСЫ РЕВИЗОРОВ** — суммарные часы каждого ревизора (из `time_log` писем).

Особенности:

- **Автоматическое определение зон** по названию события. «Алкоголь" НД» и «Алкоголь НД» распознаются одинаково — кавычки нормализуются.
- **Перепроверка расхождений — не зона.** Даже если в комментарии указана зона («Перепроверка: Заморозка»), событие уходит в «Прочие мероприятия», а не в зоны.
- **Фильтр по ГМ** через автокомплит.
- **Кнопка «Забрать информацию»** — вручную запускает сбор писем из Outlook (см. «Интеграция с Outlook»).
- **Кнопка «Сохранить как PNG»** — экспортирует весь дашборд в PNG (`Готовые/Дашборды/dashboard_{gm}_{date}.png`).
- **Встроенный режим** — когда дашборд открыт из Архива, кнопка «Забрать информацию» скрыта, заголовок меняется на «ДАШБОРД — ГМ {код}».
- Если поле ГМ пустое — показывается подсказка «Выберите ГМ».
- Если по ГМ нет писем — «Нет данных по этому ГМ».

Бизнес-логика дашборда «Общий пересчёт» вынесена в `core/dashboard_builder.py` (история действий, активная инвентаризация, архив, результаты квантов, сводки). Отдельно от UI — тестируется без PyQt.

### AI — «Стажёр» (Shadow Engine)

Вкладка для разметки объяснений решений правил от Shadow Engine.

- Таблица гипотез: ID, ключ строки, правило, уверенность, объяснение ИИ, разметка, действия.
- **Пагинация** по 100 записей.
- **Фильтры**: «Только неразмеченные», порог уверенности (≤ N), поиск по коду ТП / причине / правилу.
- **Детали строки** в боковой панели: правило (человеческое название), уверенность (цвет: красный < 0.4, жёлтый < 0.7, зелёный ≥ 0.7), код ТП, операция из РТП, наименование, ГР 20, знак (излишек/недостача), сумма потерь, номер документа, типовая причина, объяснение ИИ.
- **Разметка**: «Согласен» / «Не согласен» (SVG-иконки check/x, без эмодзи). Массовая разметка выделенных строк.
- **Экспорт** feedback в JSONL (`data/ml/exports/`).
- **Очистка базы** hypotheses с архивацией feedback (`feedback_archive.jsonl`).
- **Серый прогресс-бар** — сколько размечено из всего.

### Интеграция с Outlook

Сбор и анализ писем инвентаризации.

**Источник:** папки Outlook **«Входящие»** (Inbox), **«KRS GM»**, **«KRS_GM»**. Поиск идёт рекурсивно по подпапкам (до 5 уровней).

**Фильтр по отправителю:** `Krs_gk_gm_otchet@magnit.ru`. Проверка идёт и по `SenderEmailAddress`, и по `SenderName`, и по SMTP через `PropertyAccessor` (работает для Exchange DN).

**Фильтр по теме:** содержит одну из подстрок:

- «Отчет о ходе проведения полной инвентаризации»;
- «Отчет о завершении полной инвентаризации».

**Фильтр по дате:** `days_back=None` — **вся папка** (без отсечки). Можно указать `days_back=N` — за N дней.

**Дедупликация писем:**

- По `EntryID` — на уровне Outlook.
- По `(gm_code, report_date)` — на уровне хранилища. Если такое уже есть — новое **не сохраняется**, пишется info в лог.

**Парсинг письма** (`core/email_parser.py`):

- ГМ: код, название, формат (два формата шапки).
- Даты: начало и окончание инвентаризации.
- Длительность и вариант (А–Ж).
- Автор и дата отправки.
- Исполнители: ФИО, город, роль, телефон.
- Промежуточные итоги: за день + накопительно с/без РМ и МЦ.
- Финальные итоги: с РМ и МЦ / без (только для финальных писем).
- Подготовка к инвентаризации.
- Проведение инвентаризации: события с датой, суммой, знаком, комментарием.
- Учёт рабочего времени: смены, часы, люди.
- Дополнительные комментарии с датами.

**Финальные письма** (`is_final=True`):

- Содержат строки «Сумма полной инвентаризации c РМ и МЦ» и «Сумма полной инвентаризации без учёта РМ и МЦ».
- `report_date` берётся из `end_date` — чтобы не пересекаться по ключу с ежедневным письмом первого дня.
- Автоматически попадают в `data/inventory_archive.json`.

**Автозагрузка при старте:**

- Через 5 секунд после запуска приложения.
- В фоновом потоке. UI не блокируется.
- Показывает статус в статус-баре: «Загрузка писем из Outlook...» → «Готов».
- Без всплывающих окон. При ошибке — только запись в лог.

**Ручной сбор:** кнопка «Забрать информацию» на вкладке «Дашборд».

**Хранение:**

- `data/emails/emails.json` — список писем.
- `data/inventory_archive.json` — архив завершённых инвентаризаций (для дашборда по архиву).
- Чтение/запись — через `DataManager` (кэш по `mtime`, очередь записи, атомарная запись).

**Аналитика** (`core/email_analytics.py`):

- Последнее письмо — для итоговой суммы.
- Последнее письмо с непустыми `events` — для зон, событий, часов.
- Разбивка событий на зоны и «прочие мероприятия».
- Топ зон, топ прочих событий, часы ревизоров, «не приступали».
- История по всем письмам — для графика динамики.

### Стандартные комментарии

- Шаблоны хранятся в `data/standard_comments.json`.
- Условные блоки: при отрицательной сумме — «излишек», при положительной — «недостача».
- Форматирование сумм в русском формате (`1 234 567,89`), процентов (`12,35`).
- Автокомплит ГМ.
- Автоподстановка названия активной инвентаризации.
- Поле **«Сумма инвентаризации»**: при вводе суммы формируется фраза «Сумма инвентаризации на X руб. (Излишек / Недостача)». Если сумма пустая или 0 — «Расхождений не выявлено».

### Принтеры

- Список установленных принтеров через `win32print`.
- Установка по IP: PowerShell + `rundll32` (резервный метод). Перебор драйверов по приоритету (`Microsoft IPP Class Driver`, `Microsoft Virtual Print Class Driver` и др.).
- Переименование, установка по умолчанию, проверка доступности.
- Контекстное меню, двойной клик.

### Сетевые папки ГМ

- Поиск ГМ по коду или названию (автокомплит).
- Создание папки ПИ ГМ с пятью подпапками (1–4 сутки, Итоговые).
- Создание ярлыка на рабочем столе через `win32com` (резервный метод — PowerShell).
- Двойной клик по ГМ — сразу создать ярлык.

### Расстояние между ГМ

- Расчёт по прямой (`haversine`) и оценка по дорогам (×1.2).
- Оценка времени в пути (при средней скорости 80 км/ч).
- Кэш координат городов в `data/gm_cities_cache.json` (Nominatim / OpenStreetMap).
- Список магазинов в каждом городе.
- Кнопка «Поменять местами».

### Терминал — подключение к ГМ через mstsc

- Подключение к удалённому ГМ через `mstsc.exe`.
- Автодополнение ГМ (по коду и названию).
- Сохранение пароля через `cmdkey` (учётные данные Windows).
- Открытие RDP **отдельным окном** — Qt не умеет встраивать не-Qt окна (см. «Известные ограничения»).

### ТСД — генератор QR-кодов

- Генерация QR-кодов (тёмный фон, красные модули) для прошивки терминалов.
- Ведёт на `http://10.2.252.5:8080/hms/iface/login`.
- Библиотека `qrcode[pil]`.

### АСУС — встроенный браузер (pywv2 / WebView2)

- Встроенный браузер на **pywv2** (WebView2 Runtime). `QWebEngineView` / `PyQt6-WebEngine` **не используются** — от них отказались.
- Только ресурс **АСУС** (`https://rao.corp.tander.ru/`). Вкладки «Командировка» и «Help» убраны из Web; их URL остаются в `config.json` как зарезервированные.
- Верхняя и нижняя панели браузера отсутствуют — окно АСУС занимает всё пространство вкладки.
- **Ключевое решение:** WebView создаётся **один раз** с правильным размером. При переключении вкладок размер **не меняется** — окно скрывается/показывается через `ShowWindow` (WinAPI) в `showEvent` / `hideEvent`. Это решило проблему «съезжания» WebView.
- Cookies, localStorage, IndexedDB сохраняются между сессиями (профиль WebView2 в `data/webengine/asus/`).
- В сайдбаре (`ui/app.py`) кнопка называется **«АСУС»**.

### Нарушения (Трассировщик)

- Вход — файл с кодами + РТП (без Квантов).
- Отключены: Пересорт, Хищение, Местный поставщик.
- Оставлены: Зеркалка, Коробочный, Обычная приемка.
- Вывод: Наименование, Группа, Знак, Причина + список инвентаризаций (Дата: Кол-во).

### Информация

- Инструкция по подготовке файлов для каждого модуля.
- Сведения о программе.
- Кнопка «Скопировать инструкцию».

## Установка

### Требования

- **ОС:** Windows 10/11 (проверено на Windows 11).
- **Python:** 3.13 (совместимо с 3.11+).
- **Microsoft Visual C++ Redistributable** (обычно предустановлен).

## Архитектура

Подробная карта файлов и модулей — в отдельном документе: **[`PROJECT_STRUCTURE.md`](PROJECT_STRUCTURE.md)**. Там дерево каталогов, назначение каждого модуля, содержимое `%LOCALAPPDATA%\Core_V3_0\data\` и точки расширения. Здесь — только принципы разделения слоёв.

### Слои приложения

- **`ui/`** — только пользовательский интерфейс. Бизнес-логика отсутствует.
- **`core/`** — бизнес-логика. Не зависит от PyQt.
- **`ml/`** — Shadow Engine. Не зависит от PyQt.
- **`utils/`** — утилиты. Не зависит от PyQt. Полностью тестируемо.
- **`data/`** — данные в формате JSON, в `%LOCALAPPDATA%`. Изменяются без правки кода.

### Работа с потоками

- `BaseFrame.run_in_thread` — запуск фоновой задачи.
- `BaseFrame.run_on_ui` — безопасный вызов UI-функций из фонового потока. Реализовано через `pyqtSignal`: Qt автоматически доставляет вызов в главный поток.
- `AuditApp._status_call` — сигнал для обновления статус-бара из фоновой автозагрузки писем.
- `BaseFrame.on_hide` / `on_close` — хуки, вызываемые `AuditApp` при переключении вкладки и при закрытии. Используются в `inventory_frame` для сохранения чек-листа до скрытия/выхода.

### Хранение данных

- `DataManager` — singleton, JSON-хранилище с кэшем по `mtime`, очередью записи и атомарной записью через `.tmp` + `os.replace`.
- Все модули (включая `email_storage`) читают и пишут только через `DataManager`. Это даёт единый кэш и единую очередь записи.

## Данные

Данные ревизора живут не в корне проекта, а в:

```text
%LOCALAPPDATA%\Core_V3_0\data\
```

Это нужно, чтобы программа работала из `Program Files` и не теряла данные при обновлении. Миграция старой `data/` из корня проекта выполняется один раз при первом запуске:

- `utils/data_migration.py` — логика миграции;
- флаг `.migrated` в `%LOCALAPPDATA%\Core_V3_0\` — защита от повторного запуска;
- только копирование, оригинал в корне не удаляется;
- существующие файлы в целевой папке не перезаписываются.

Путь к данным возвращает `utils/file_utils.get_data_dir()`. Все модули (`core/timesheet.py`, `core/dashboard_builder.py`, `email_storage`, `DataManager` и т.д.) обязаны использовать его, а не хардкодить `<корень>/data`.

Начиная с этой версии, `standard_comments.json` также читается из `%LOCALAPPDATA%\Core_V3_0\data\` через `DataManager` (`STANDARD_COMMENTS_PATH`), а не из корня проекта.

## Разработка

### Стиль кода

- Type hints — везде, где возможно.
- Docstrings — на каждом модуле, классе и публичном методе.
- Конкретные исключения вместо общего `except Exception`.
- Осмысленное логирование через `utils/logger.py`.
- Магические числа выносятся в константы.
- Дублирование устраняется.
- Разбиение файлов — по принципу единственной ответственности (SRP), а не ради метрик.

### Логирование

Логи пишутся в `%LOCALAPPDATA%/Core/Logs/core.log` с ротацией (2 МБ × 5 файлов). Дублируются в консоль с уровнем INFO. Буфер сбрасывается после каждой записи — логи видны в реальном времени.

Если `%LOCALAPPDATA%` недоступна — лог пишется в `Logs/` рядом с проектом.

### Принципы

| Принцип | Описание |
|---------|----------|
| Работает — не трогаем | Работающий и читаемый код не переписывается |
| Логика важнее формы | Не разбиваем файлы ради метрик |
| Тесты — на логику | Покрытие бизнес-правил, не UI |
| Данные отделены от кода | Правила — в JSON |
| Единый стиль | SVG-иконки, тёмная тема |

**Как отправить изменения на GitHub:**
```bash

Приложение использует Windows-специфичные API:

- `win32print` — список и управление принтерами;
- `win32com.client` — создание ярлыков, доступ к Outlook;
- `os.startfile` — открытие папок в Проводнике;

### 2. RDP-сессии не встраиваются в Core

Вкладка «Терминал» использует `mstsc.exe` — стандартный клиент удалённого рабочего стола Windows. Это стороннее окно, не Qt. Qt не поддерживает встраивание не-Qt окон в свой контейнер.

Единственный рабочий вариант — открывать RDP отдельным окном. Это ограничение операционной системы, а не приложения.

### 3. WebView2 Runtime требуется для вкладки «АСУС»

Вкладка «АСУС» использует `pywv2` (WebView2). Для работы нужен **Microsoft Edge WebView2 Runtime**:

- на Windows 11 обычно уже установлен;
- на Windows 10 может потребоваться отдельная установка (Evergreen Runtime с сайта Microsoft).

Если Runtime отсутствует — WebView2 не создастся, вкладка покажет ошибку. Это не ломает остальное приложение.

Дополнительно: WebView создаётся **один раз** с фиксированным размером, а при переключении вкладок скрывается/показывается через `ShowWindow`/`HideWindow`. Изменение размера окна WebView2 «на лету» приводило к съезжанию — поэтому размер задаётся при создании и дальше не трогается.

### 4. `xlrd` нужен для чтения `.xls`

Современный pandas использует `openpyxl` для `.xlsx` и `xlrd` для `.xls`. Модуль `os_mbp_analyzer` умеет читать оба формата — потому что выгрузки ИНВ-1 из 1С часто приходят именно в `.xls`.

Если `xlrd` не установлен — при попытке прочитать `.xls` будет:

```text
ImportError: `Import xlrd` failed. Install xlrd >= 2.0.1 for xls Excel support
```

Решение: `py -3.13 -m pip install "xlrd>=2.0.1"`.

### 5. `pywin32` нужен для принтеров и ярлыков

Модули «Принтеры» и «Сетевые папки» используют `pywin32`:

- `win32print` — список принтеров, установка по умолчанию;
- `win32com.client` — создание `.lnk` на рабочем столе.

Если `pywin32` не установлен — вкладка «Принтеры» покажет ошибку `No module named 'win32print'`, а создание ярлыка уйдёт в fallback через PowerShell (медленнее, но работает).

Решение: `py -3.13 -m pip install pywin32`.


### 6. Автозагрузка писем из Outlook

Автозагрузка писем (через 5 секунд после старта) работает только если Outlook установлен и настроен на этой машине.

Если Outlook не установлен:

- COM-подключение упадёт;
- в логе будет запись `auto_fetch: ошибка сбора писем`;
- приложение продолжит работать — это некритичная функция.

Автозагрузка не блокирует UI: идёт в отдельном потоке, обновляет статус-бар внизу через сигнал.

### 7. Сбор писем — только с локального Outlook

Сбор работает через COM-подключение к локально установленному Outlook (`win32com.client.Dispatch("Outlook.Application")`). Это значит:

- Exchange Online / OWA — не поддерживается напрямую. Нужен настроенный локальный Outlook-профиль.
- Несколько профилей Outlook — используется тот, что открыт по умолчанию.
- Права доступа — если Outlook запускается от имени другого пользователя, COM может не подключиться.

Если письма лежат в Exchange, но Outlook локально не настроен — сбор не сработает. В этом случае нужно использовать другой способ (например, `exchangelib` для Exchange Web Services), но это уже за рамками текущей реализации.

### 8. `data/` в корне — только legacy

После переноса данных в `%LOCALAPPDATA%\Core_V3_0\data\` папка `data/` в корне проекта — legacy. Её подхватывает `utils/data_migration.py` при первом запуске и копирует в новое место. После успешной миграции (есть флаг `.migrated`) старую `data/` можно удалить вручную. Программа без неё работает.
